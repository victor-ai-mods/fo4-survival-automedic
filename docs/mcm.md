## Что сделано

```
data/mcm.json ──tools/gen_mcm.py──┬─> build/mcm/MCM/Config/SurvivalAutoMedic/config.json   (только $AM_*)
                                   ├─> build/mcm/Interface/Translations/SurvivalAutoMedic_en.txt
                                   ├─> build/mcm/Interface/Translations/SurvivalAutoMedic_ru.txt
                                   └─> papyrus/AutoMedicSettings.psc                        (33 свойства)
```

* **Один источник.** Структура страниц, дефолты, диапазоны и тексты на обоих
  языках — в `data/mcm.json`. Ключи генерируются из id: `$AM_<id>`, `$AM_<id>_HELP`,
  `$AM_<список>_<n>`. Руками ключи нигде не пишутся.
* **Генератор падает**, если у строки нет перевода на язык из `languages`, если id
  повторяется, дефолт вне диапазона, а после сборки — если в `config.json` есть токен
  без перевода или в переводе лишний ключ. Проверено: удалённый `help.ru` у
  `HealTargetPct` → `gen_mcm: ОШИБКА: PAGE_HEALTH/HealTargetPct (help): нет перевода на ru`, код 1.
* **Новый язык:** `python tools/gen_mcm.py --template de` выдаёт все ключи с английским
  текстом в комментарии; перевод вписывается в `mcm.json` (строка `"de"` в каждом тексте
  и `de` в `languages`).
* **Файл перевода:** UTF-16 LE с BOM, CRLF, `$КЛЮЧ<TAB>текст` — как у LootMan/LIF.

### Где живут настройки

Новый квест **`AM_Settings`** (`SurvivalAutoMedic.esp|808`) с единственным скриптом
`AutoMedicSettings`. MCM читает и пишет его свойства (`PropertyValueBool/Int`).

* Почему не третий скрипт на `AM_Quest`: в `PropertyValue*` нет имени скрипта
  (`scriptName` в MCM есть только у `CallFunction` и `listFromProperty`), а на
  `AM_Quest` уже два скрипта — у какого MCM станет искать свойство, неизвестно.
* Почему не `ModSetting*` + ini: дефолт свойства — инициализатор в самом скрипте,
  значение есть с первой загрузки. Баг «switcher читается как false, пока его не
  тронули» (§7) бывает у `ModSetting*` без `settings.ini`; здесь ему неоткуда взяться.
  Отдельный init-скрипт дефолтов на `OnQuestInit` поэтому не понадобился — его роль
  выполняет кнопка «Сбросить все настройки» (`ResetDefaults`, тоже сгенерирована).
* `AutoMedicQuestScript.LoadSettings()` раз за нажатие копирует свойства в свои
  переменные (бывшие константы `HUNGER_TRIGGER`, `LOG_LEVEL`, …). Чтение свойства
  чужого скрипта — вызов в другой объект, а планировщик читает резервы и пороги на
  каждом кандидате.
* В лог (уровень ≥ Сводка) пишется строка `SETTINGS …` — при первом нажатии сессии
  и при каждой смене настроек. По ней и проверяется приёмка.

**Расхождения с §7 плана (осознанные):**
* В MCM только то, что код уже умеет. Автоматический режим (шаг 9), перехват сна,
  кофе, перегруз, кола/ОД, `iLastResortFood`, веса `cost`, `bLogToConsole`,
  `iRenameItem` появятся вместе со своей логикой — пустой тумблер хуже отсутствующего.
* `LogLevel` по умолчанию **Сводка**, а не Off: одна строка на нажатие ничего не стоит,
  а без лога нечего приложить к сообщению об ошибке и нечем проверить дефолты.
* `MaxItemsPerNeed` по умолчанию 12, а не 6 — под SCM из Hungry нужно до 12 штук (шаг 6).
* Списки стадий разные: «начинать с» — 1..5 (без «Сыт»/«Жажды нет»: с нулевой стадии
  есть незачем), «до» — 0..4 (без «Истощения»). Общий список в `mcm.json` один,
  вырезку задают `first`/`last`; свойство `HungerFrom`/`ThirstFrom` хранит индекс,
  стадия = индекс + 1. Если «до» не ниже «начинать с», скрипт опускает цель на стадию
  ниже. Первая сборка (00:02) показывала все шесть стадий в обоих списках — исправлено
  по замечанию пользователя; свойства переименованы из `*Trigger`, чтобы старое значение
  из сейва не сдвинуло стадию.
* Русские названия стадий — свои, не игровые: в русской локализации игры Peckish и
  Starving оба «Голод», Parched — «Сильная жажда» (сверено по `fallout4_ru.strings`).
* `displayName` — тоже токен `$AM_MOD_NAME` (A21): у LIF он токеном и работает.
  Текст в обоих языках одинаковый — «Survival AutoMedic».

### Свой файл лога (2026-09-22 01:07)

MCM «Диагностика» → «Куда писать лог»: никуда / **свой файл** (по умолчанию) / лог Papyrus / оба.
Свой файл — `Data\SurvivalAutoMedic\AutoMedic.log` через `GardenOfEden3.WriteLinesToFile`: не нужны
`bEnableLogging`/`bEnableTrace` (с ними игра подтормаживает — замечание пользователя) и читается
прямо во время игры, без буферизации до выхода. Прошлая сессия — `AutoMedic.1.log`, больше 1 МБ —
ротация по ходу сессии. Строки копятся в буфер и пишутся одной записью в конце цикла, каждую
секунду WATCH и при 100 строках (массив через `Add` упирается в 128).
* **Режим записи неизвестен:** документация GOEPE (v23.6, `docs/GOEPE/`) говорит только, что с
  флагом файл перезаписывается. Без флага — дописывает или нет, не сказано. Поэтому
  `LogProbeAppend` на каждой загрузке пишет пробную строку и сравнивает `GetFileSize` до/после:
  вырос — дописывание, нет — запасной путь «прочитать → слить (`MergeArraysString`) → перезаписать».
  Результат — строка `Лог: … — размер A -> B байт` в начале файла и `лог N -> файл (дописывание)`
  в `SETTINGS`.
* Цель можно переключить посреди игры: `LoadSettings` → `SetLogTarget` откроет недостающее.
* **Прогон 01:32–01:46:** режим — «перезапись» (`WriteLinesToFile` без флага вернул False, размер
  44 → 44), кириллица в UTF-8 читается, циклы и `SETTINGS` на месте — M14 пройден.
  Но смерть и автозагрузка затёрли лог: каждая загрузка начинала файл заново. **С 01:52** файл
  при загрузке продолжается (разделитель `=== загрузка сохранения, <дата> ===`), в `.1`/`.2`
  уходит только по размеру (512 КБ — каждая запись перечитывает файл целиком).
