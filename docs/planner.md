# Шаг 5 — планировщик

Фазы 1–2 плана (§4.2–4.3): жадное покрытие нужд по ОЗ и радиации, конечности, болезни и
зависимости, обрезка. Всё ещё dry-run: план пишется в лог и в уведомление, ничего не тратится.
Голод и жажда не планируются — их закрывает замкнутый цикл шага 6.

Код — `papyrus/AutoMedicQuestScript.psc` (`EvalCandidates`, `Plan`, `BestFor`, `Trim`).
Офлайн-зеркало для проверки алгоритма без игры — `tools/plan_sim.py`.

## Стадии

`A` радиация → `B` конечности → `D` болезни и зависимости → `C` здоровье → `A'`/`C'` добор.

- **A.** Нужда = `rads − в полёте − цель`, только если `rads ≥ порог` (M11). Жадно по `gain/cost`.
  Лечение рад-предметов (Nuka-Grape +100, Chops +60) идёт в зачёт ОЗ на стадии C.
- **B.** Один стимпак на все конечности (A6). Если стимпак уже капает (`InFlight stimpak > 0`) —
  второй не берётся (M6). Резерв стимпаков соблюдается: остаются только резервные → `UNMET`.
- **D.** Один предмет на болезни, один на зависимости, самый дешёвый по `cost` со скидкой за
  попутное лечение. Еда-лекарство (омлет) — только если голод закроется.
- **C.** Нужда по ОЗ пересчитывается от потолка **после** запланированного вывода (M1) и минус
  «в полёте». **С 2026-09-22 — не жадно по цене, а набор с минимальным перелечением**
  (решение пользователя: цена в крышках решает только голод; «осталось 80 — лучше 40 + 50, чем
  одна на 110»). Перебор с отсечениями (`HealSearch`, бюджет 1000 узлов) сравнивает наборы по
  ключу (добран ли с допуском, потери ОЗ, штук, cost): потери = перелечение (или недобор) +
  `rads_еды × maxHP/1000`. Порога `MIN_SCORE_HP` больше нет; грязная вода и прочее с риском и
  немедленной проверкой на ОЗ не берутся. Поводом стал лог #38: при нужде 181 и Medic 3 брался
  стимпак на 389 ОЗ, хотя еды было много.
- **A'/C'.** Если лечащая еда принесла радиацию сверх порога (M2) — добор вывода и ещё раз ОЗ.
- **Обрезка.** Строка плана убирается, если без неё ни одна нужда не становится хуже (в пределах
  допуска); из таких — самая дорогая, пока есть что убрать. Конечности/болезни/зависимости не трогаются.

## Цена `cost(i)`, крышки

```
cost = цена
     + 5                              ; каждая штука (иначе 400 ОЗ = 20 морковок)
     + 5 × риск% × (2, если немедленная проверка)   ; M14
     + 60 за иммунодефицит (15, если он уже есть или будет от другого предмета плана)
     + 10 / сколько штук осталось     ; дефицит
```

Ограничения кандидатов (дефолты §7): цена ≤ 150, риск ≤ 7 %, резерв 2 стимпака и 1 RadAway,
не более 50 rad едой за цикл; без средств вывода — не переходить порог радиации (решение 1);
аддиктивная химия и алкоголь выключены. Чёрный список дополнен (`gen_psc.PLANNER_BLACKLIST`):
Refreshing Beverage (в Survival 100 rad, не 1000), Mysterious Serum (−36000 — это AbsorbRads
на час), Robot Repair Kit, служебные антибиотики.

## Скорость

Шаг 3 мерил цикл в ~5.2 с: инвентарь 3.8 с (76 мс на предмет, ~7 вызовов с ожиданием кадра),
болезни/зависимости 0.63 с, перки 0.36 с. Теперь:

- **инвентарь** — 2 вызова на стопку: `GetNthItemFormID` → строка таблицы через `FindStruct` по
  новому полю `FullId` (полный FormID считается в `BuildTables`: индекс загрузки DLC находится
  перебором `Game.GetForm(idx·2²⁴ + local)`); `GetNthItemCount` — только для нужных сейчас предметов.
  Цена (`GetGoldValue`) и имя — из кеша сессии. **Нужд нет — инвентарь не читается вовсе**;
- **болезни, зависимости, иммунодефицит, Рад-X, снадобья** — из того же снимка `GetActiveEffects`;
  для болезней и прочего старый способ (`HasMagicEffect`) остался сверкой на уровне Trace
  (`Status check`). Зависимости сверять не с чем: `HasSpell` настоящую зависимость не видит (G8');
- **перки** — не чаще раза в 30 с.
