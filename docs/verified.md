## Подробности

### M3 / A8 — насыщение

**Ваниль** (`ModFoodPoolAndUpdateHungerEffects`, жажда устроена так же):

```
вклад = GetGoldValue(предмет)
вклад = min(вклад, 231)                 ; жажда: 167 — один потолок, от стадии НЕ зависит
вклад = max(вклад, пол[текущая стадия]) ; еда  Fed..Starving: 12 12 12 24 24 56
                                        ; вода Hyd..SevDeh:   8  8 10 18 24 30
вклад *= 0.5, если «Паразиты»
FoodReqs += вклад;  Fed при FoodReqs >= 0
```

Пороги стадий по `FoodReqs`: −24 / −48 / −96 / −144 / −256 (вода −16 / −36 / −72 / −120 / −180).
При ухудшении стадии `FoodReqs` ставится ровно на порог новой стадии, дальше убывает на 4 в час
(и еда, и вода; во сне — вчетверо медленнее).

Что это меняет в плане:
- «пол ≈ половина стадии» — неверно, пол — фиксированные числа выше;
- «почти любую стадию закрывают 2 предмета» — **неверно для дешёвой еды**: из Hungry до Fed нужно
  48…96 очков, при поле 12 это **4–8 предметов**; из Starving (256+) при поле 56 — ~5;
- следствие для ранжирования: всё, что дешевле пола текущей стадии, даёт **ровно пол** — среди
  таких предметов выбирать по цене бессмысленно, они равноценны по насыщению.

**SCM (эта сборка)**: `SCM_HC_FoodUseWeight = SCM_HC_DrinkUseWeight = 1` по умолчанию, настроек
MCM пользователь не менял → насыщение считается **по весу**, причём с перевёрнутой проверкой в
`getWeightWithFallback`: у предмета с весом 0 получается 0 (→ пол стадии), у предмета с весом —
`0.5 × 240 = 120`, дальше множитель «качества» 0.7…2.0 по ключевым словам SCM. Подтверждено
`Hardcore.0.log`: `return weight of item0.000000 … Player is Fed! Updated ModPoolAmount: 8`.

**Вывод:** предсказывать насыщение по таблице нельзя ни в ванили (пол и порог зависят от скрытого
`FoodReqs`), ни тем более под SCM. **Замкнутый цикл §1.1 — единственный надёжный путь**, решение
плана подтверждено. Цикл гарантированно сходится: каждый предмет даёт не меньше пола стадии.

**Новое для шага 6:** `HC_Manager` обрабатывает еду **асинхронно** — `OnItemEquipped` кладёт предмет
в очередь, `ProcessFoodItems` идёт через `CallFunctionNoWait` с `WaitMenuMode(0.1)` между
предметами. Сразу после приёма AV ещё старый. Цикл «съел → перечитал» обязан ждать смены AV
(опрос с таймаутом), иначе съест лишнее.

### M4 — подавление эффектов еды при голоде

Перк `HC_SustenanceEffectsTurnOffFood` (`0x0008B2`), который `HC_Manager` выдаёт игроку на старте
Survival. Две точки входа — `Mod Incoming Spell Magnitude` и `Mod Incoming Spell Duration`, обе
«установить 0», при условиях:

- `HC_Rule_SustenanceEffects == 1` **и** `HC_HungerEffect > HC_HE_Fed` — то есть уже с Peckish;
- у предмета есть `ObjectTypeFood` и нет `HC_IgnoreAsFood` (для магнитуды — ещё и нет `ChemEffect`).

Точно как в вики. Два следствия, которых в плане не было:
1. Проверка идёт **в момент применения эффекта**, а насыщение считается позже (асинхронно, см. выше).
   Еда, съеденная голодным, **не лечит никогда** — даже та, что сама довела до Fed.
2. Дикие растения (`HC_IgnoreAsFood`) под перк не попадают — их бафы работают всегда (A2b).

SCM этот перк не переопределяет.

### M13 / A14 / A20 — травяные снадобья и проверка болезни

`CheckAndPossiblyApplyDisease`:
1. бросок `r` ∈ [0.01, 1]; болезнь, если `r ≤ DiseaseRiskPool × (1.2 при иммунодефиците)`;
2. если в этот раз принимали антибиотики — бросок принудительно мимо;
3. болезнь **выбирается случайно** из 6; если у игрока активен эффект снадобья **для этой болезни** —
   болезнь только при `r ≥ 0.2`.

| Снадобье | Защищает от |
|---|---|
| Antimicrobial `0x249F9A` | Паразиты, Инфекция |
| Stimulant `0x249F9B` | Летаргия, Усталость |
| Anodyne `0x249F9C` | Бессонница, Слабость |

Когда идёт проверка: **при каждом начале сна** (`OnPlayerSleepStart` → `CheckForDiseaseAndRestart`)
и через ~2 игровые минуты после «рискового» события, если пул > 0.25. Сутки после болезни —
льготный период без бросков.

Что это меняет:
- «окно 1 игрового часа» — неверно: нужно лишь, чтобы эффект **был активен в момент проверки**.
  Длительность эффекта в esm — 3600 с реального времени (≈20 игровых часов при timescale 20;
  возможно, ×10 в Survival — T3);
- одно снадобье покрывает только 2 болезни из 6; полная защита — все три;
- «−20 %» — это не вычитание из шанса, а отсечение бросков ниже 0.2 для болезней своей пары;
- A20: наш `OnPlayerSleepStart` гоняется с обработчиком `HC_Manager` — пить надо раньше.
  `OnSit` на кровать в игре не пришёл ни разу (2026-09-24) — пьём при открытии `SleepWaitMenu`,
  если занятая мебель с `IsSleepFurniture`. При длительности ~20 игровых часов запаса более чем достаточно.

### A22 — откуда растяжение

GMST `fDiffMultEffectDuration_SV` и `fDiffMultEffectDuration_TSV` = **10.0**. Движок умножает
длительность и делит магнитуду (итог тот же — это и видно на стимпаке и еде в шаге 3). На
каких эффектах — не выяснено: стимпак и еда да; RadAway, снадобья, бафы — T2/T3.

### Найдено попутно: инструмент AutoMedic сушил игрока

У предмета стоит `ObjectTypeStimpak` (ради вкладки «Помощь»), а стимпак входит в
`IncreasesThirstKeywords`. Под SCM (`HungerThirstGainAlt`) каждое нажатие отнимало **2 очка
жажды** — видно в `Hardcore.0.log`: `increasing thirst by weight: [Potion < (39000804)>], cost: -2`.
В ванили потеря 0 только потому, что цена предмета 0. **Исправлено:** на предмет добавлено
`HC_IgnoreAsFood` — `OnItemEquipped` и ванили, и SCM пропускает всё с `NonFoodKeywords`.

### Прочие факты для следующих шагов

- `HC_SleepEffect`: 0 = Well Rested / Lover's Embrace, 1 = Rested, 2 = Tired … 6 = Incapacitated
  (в скрипте шага 3 шкала была сдвинута на 1 — исправлено).
- Nuka-Cola (ваниль): жажда `+0.4 × цена`, голод `−0.2 × цена`; `IncreasesHunger` — `−0.65 × цена`,
  `IncreasesThirst` — `−0.5 × цена`. Под SCM вместо цены — плоские `4 × множитель`.
- Химия с риском, стандартная и высокорисковая еда вызывают **немедленную** проверку болезни
  (`HandleDiseaseRiskEvent` → таймер 0.033 игр. часа), если пул выше 0.25.
- Антибиотики не только лечат: следующий бросок болезни гарантированно мимо.
